# 排版意向系统接口与数据规范

版本：V1.0  
当前实现范围：标准化骨架、人工校正、排版模式库、结构化业务需求、场景化匹配、
三个排版意向方向、低保真预览、方向选择与调整反馈。

## 1. 兼容性边界

- 保留 SQLAlchemy + SQLite。
- 保留 `/api/analyze`、`/api/search`、`/api/cases/{id}`。
- 不删除或覆盖现有数据库。
- `layout_blueprints` 由 `Base.metadata.create_all()` 创建。
- 兼容迁移会为已存在但字段不完整的 `layout_blueprints` 补齐字段。

## 2. LayoutBlueprint

一个案例可以拥有多个版本的排版骨架。人工校正通过新增版本保存，历史版本保持不变。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | integer | 主键 |
| `case_id` | integer | 来源案例 |
| `canvas_ratio` | string | 画布比例，如 `2:3` |
| `orientation` | enum | `portrait`、`landscape`、`square` |
| `grid_columns` | integer | 栅格列数，1～24 |
| `grid_rows` | integer | 栅格行数，1～48 |
| `margins` | object | 上右下左归一化边距 |
| `alignment` | string | 主对齐策略 |
| `reading_flow` | string | 阅读动线 |
| `focal_region` | object/null | 主视觉区域 |
| `information_density` | string | 信息密度 |
| `text_image_ratio` | number | 文字占比，0～1 |
| `module_count` | integer | 模块数量 |
| `modules_json` | array | 标准化模块列表 |
| `version` | integer | 案例内版本号 |
| `review_status` | enum | `ai_unverified`、`human_edited`、`verified` |
| `model_name` | string | 生成模型名称 |
| `prompt_version` | string | Prompt 版本 |
| `editor` | string | 人工编辑者 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

## 3. 归一化坐标规则

`x`、`y`、`width`、`height` 均以画布为基准，取值范围为 0～1：

- `x + width <= 1`
- `y + height <= 1`
- `width > 0`
- `height > 0`
- 同一骨架内模块 `id` 不得重复
- `module_count == len(modules_json)`

示例：

{

  "orientation": "portrait",
  "grid_columns": 6,
  "grid_rows": 12,
  "margins": {

    "right": 0.06,
    "bottom": 0.05,
    "left": 0.06
  },
  "alignment": "center",
  "reading_flow": "top-to-bottom",
  "focal_region": {
    "x": 0.18,
    "y": 0.22,
    "width": 0.64,
    "height": 0.46
  },
  "information_density": "medium",
  "text_image_ratio": 0.35,
  "module_count": 2,
  "modules_json": [
    {
      "id": "module-1",
      "type": "title",
      "x": 0.08,
      "y": 0.05,
      "width": 0.84,

      "priority": 1,
      "alignment": "center",

    {

## 4. HTTP API

| 方法 | 地址 | 说明 |
|---|---|---|
| `GET` | `/api/cases/{case_id}/layout-blueprints` | 获取案例全部骨架版本，最新版在前 |
| `POST` | `/api/cases/{case_id}/layout-blueprints/generate` | 根据图片比例和现有拆解生成下一版启发式骨架 |
| `GET` | `/api/layout-blueprints/{blueprint_id}` | 获取指定骨架版本 |
| `POST` | `/api/layout-blueprints/{blueprint_id}/revise` | 保存人工修订为新版本 |
| `POST` | `/api/layout-blueprints/{blueprint_id}/verify` | 将当前内容复制为已确认新版本 |

人工修订请求使用完整 `LayoutBlueprintInput`。`review_status` 会被服务端固定为
`human_edited`，并要求 `editor` 非空。确认接口请求：

```json
{
  "editor": "设计负责人姓名"
}
```

新上传案例在 `/api/analyze` 入库事务中自动创建首版骨架。骨架生成不调用图片生成
API，也不生成完整设计成品。

V2 骨架会读取原图的边缘投影，检测内容边界、纵向区段和列组，再用框体表达实际
模块位置。无法稳定识别时才回退到方向模板，并分别记录
`layout-blueprint-region-detection-v2` 或
`layout-blueprint-template-fallback-v2`。

## 5. 内部 CRUD

阶段 A1 提供以下内部 CRUD 契约，供后续人工校正 API 和排版模式沉淀复用：

| 函数 | 说明 |
|---|---|
| `create_layout_blueprint(db, case_id, payload)` | 创建首版或下一版骨架 |
| `get_layout_blueprint(db, blueprint_id)` | 按 ID 读取 |
| `get_latest_layout_blueprint(db, case_id)` | 读取案例最新版 |
| `list_layout_blueprints(db, case_id)` | 按版本倒序读取全部版本 |
| `revise_layout_blueprint(db, blueprint_id, payload)` | 新建修订版，不覆盖旧版 |
| `serialize_layout_blueprint(blueprint)` | 转换为结构化输出 |

现有公开 API 契约保持不变。

## 6. 旧案例回填

先预览：

```powershell
backend\.venv\Scripts\python.exe backend\scripts\backfill_layout_blueprints.py
```

确认后执行：

```powershell
backend\.venv\Scripts\python.exe backend\scripts\backfill_layout_blueprints.py --execute
```

脚本只选择没有任何骨架版本的案例，因此可重复运行且不会覆盖原案例、分析或已有骨架。

已有 V1 骨架升级为区域检测 V2 时，先预览再执行：

```powershell
backend\.venv\Scripts\python.exe backend\scripts\upgrade_layout_blueprints_v2.py
backend\.venv\Scripts\python.exe backend\scripts\upgrade_layout_blueprints_v2.py --execute
```

升级只追加新版本；最新版本已是 V2 的案例会跳过。

## 8. LayoutPattern 排版模式库

排版模式只能从 `review_status=verified` 的排版骨架沉淀。模式复制骨架的画布、
栅格、模块坐标和比例，同时保留下列证据与适用条件：

- `source_blueprint_ids`：来源骨架版本。
- `source_case_ids`：由骨架自动反查的来源案例。
- `industry_tags`、`scene_tags`、`channel_tags`、`business_goal_tags`。
- `usage_notes`：适用说明。
- `version`：同名模式每次修订或确认均创建新版本。
- `model_name=human-distilled-layout-pattern`。
- `prompt_version=layout-pattern-distillation-v1`。

| 方法 | 地址 | 说明 |
|---|---|---|
| `GET` | `/api/layout-patterns` | 查询模式，可按方向、场景、渠道、状态筛选 |
| `POST` | `/api/layout-patterns` | 从一个或多个已确认骨架沉淀模式 |
| `GET` | `/api/layout-patterns/{id}` | 获取指定模式 |
| `POST` | `/api/layout-patterns/{id}/revise` | 创建同名下一版本 |
| `POST` | `/api/layout-patterns/{id}/verify` | 创建已确认的同名下一版本 |

前端 `/patterns` 展示纯框架模式库；案例详情校正台可将当前已确认骨架直接沉淀。

## 9. 结构化业务需求与场景化匹配

`business_requirements` 将真实需求保存为独立业务对象，主要字段包括：

- 需求标题、完整描述、行业、产品品类。
- 渠道、业务场景／营销阶段、业务目标。
- 画布比例、方向、信息密度。
- 目标受众、核心信息、必须出现的元素。
- 指定参考案例、创建人和状态。

匹配只使用人工确认的排版模式与人工确认的案例骨架，不读取公司偏好评分。结果分别
返回模式匹配与案例匹配，每条结果包含可解释分数和匹配原因。

| 方法 | 地址 | 说明 |
|---|---|---|
| `GET` | `/api/business-requirements` | 查询已保存需求 |
| `POST` | `/api/business-requirements` | 保存结构化需求 |
| `GET` | `/api/business-requirements/{id}` | 获取需求 |
| `POST` | `/api/business-requirements/{id}/match` | 匹配确认模式与案例骨架 |

前端 `/intentions` 提供结构化表单、模式框架预览和来源案例入口。

## 10. 三个排版意向方向

每次生成固定返回三个结构化方向：

1. `conservative`：稳健沿用最高匹配模式。
2. `balanced`：保留层级并强化产品主视觉。
3. `exploratory`：将辅助信息拆分为更明确的分区。

方向保存完整低保真模块、来源模式、来源案例、适用原因、生成版本、模型名称和
Prompt 版本。配置文本模型时，模型只优化方向名称和理由，不改变骨架证据；调用失败
或未配置时使用启发式结果，并在 `failure_reason` 中记录原因。

| 方法 | 地址 | 说明 |
|---|---|---|
| `GET` | `/api/business-requirements/{id}/directions` | 获取全部生成历史 |
| `POST` | `/api/business-requirements/{id}/directions/generate` | 生成下一版三个方向 |

前端意向页使用与案例、模式库一致的纯框架渲染器预览三个方向。

## 11. 方向选择与调整反馈

反馈使用独立的 `layout_direction_feedback` 追加记录，不写入旧的公司偏好事件表。
支持：

- `selected`：选择该方向。
- `adjustment_requested`：记录需要调整及原因。
- `adjusted_confirmed`：保存调整后的归一化模块快照。
- `rejected`：淘汰该方向。

调整后的模块继续遵守 0～1 坐标、边界和唯一模块 ID 规则。

| 方法 | 地址 | 说明 |
|---|---|---|
| `GET` | `/api/layout-directions/{id}/feedback` | 获取追加式反馈历史 |
| `POST` | `/api/layout-directions/{id}/feedback` | 记录选择或调整结果 |

意向页可直接选择、淘汰、填写调整原因，并通过数字表单修改模块坐标后保存调整版。
